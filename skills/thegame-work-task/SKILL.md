# TheGame 업무 추적

사용자가 이 스킬을 호출하거나 TheGame 업무임이 확인된 작업의 시작·PR 연결·마감을 요청할 때 적용한다. 개인 작업·다른 회사 업무·소속이 불분명한 일반 요청은 추적을 생략한다. 이전 세션의 링크나 같은 저장소에서 작업한다는 사실만으로 새 요청을 TheGame 업무로 분류하지 않는다.

TaskBoard의 Task 한 장을 업무 기준으로 삼는다. 메인 세션이 Notion을 기록한다. 훅이 알려준 URL은 재개 단서다. 현재 요청과 같은 업무인지 확인한 뒤 사용한다.

## 시작과 재개

1. [TaskBoard](https://app.notion.com/p/33b8a6cfb7d48026833cc7effb3b6111?v=33b8a6cfb7d481328940000c2f0e3a80&source=copy_link)를 Notion MCP로 읽고 연결된 사용자를 확인한다. Git 워크트리에서는 작업 디렉터리에서 이 스킬의 [task_state.py](scripts/task_state.py)를 절대 경로로 실행한다. `python3 <스크립트> show`로 기억된 Task URL을 확인한다.
2. 사용자가 지정한 Task, 기존 basic-team 보고의 Task URL, 워크트리에 기억된 URL 또는 Scrum TODO의 실제 링크로 기존 Task를 확인한다. 제목만 같은 항목을 임의로 선택하지 않는다. 같은 업무면 재사용하고, 착수하는 TODO는 `IN PROGRESS`로 바꾼다. 사용자가 완료된 업무를 다시 열었으면 Task를 `IN PROGRESS`로 바꾸고 해당 Scrum TODO도 미완료로 되돌린다. 완료 동기화 도중 끊겼다면 아래 완료 절차의 빠진 변경만 복구한다.
3. 신규 업무라면 TaskBoard의 데이터 소스(기존 ID `33b8a6cf-b7d4-8106-bca5-000bef4c35a9`)에 하나 만든다. 실제 스키마에 맞춰 `업무명`, `Status = IN PROGRESS`, `작성자`와 `담당자`는 연결된 사용자, `작업유형`은 요청 유형, `프로젝트`는 저장소와 일치하는 기존 옵션을 사용한다. 본문에 목표와 완료 기준을 짧게 적는다. Task를 확인하거나 생성한 직후 `python3 <스크립트> remember <Task-URL>`로 기억한다. 다른 Task를 이미 기억 중이면 덮어쓰지 않고 두 URL을 구분해 전달한다. Git 밖이거나 로컬 기록이 실패하면 Task URL을 사용자에게 전달하고 Scrum 또는 팀 보고의 링크로 재개한다.
4. 처음 연결하거나 오늘 TODO에도 올려 달라는 요청이 있으면 [Daily Scrum](https://app.notion.com/p/Daily-Scrum-38b8a6cfb7d480cdb99fc194eba2e5bb?source=copy_link)에서 사용자 현지 날짜와 본인에 해당하는 기록, TODO 형식을 찾는다. 오늘 기록이 비었으면 확인된 일별 템플릿이나 기존 형식으로 만든다. 쓰기 위치가 불분명하면 그 위치만 확인한다. 체크박스면 업무명에 Task 링크를 걸고, 관계 속성이면 기존 관계에 Task를 추가한다. 이미 연결돼 있으면 그 항목을 사용한다. 각 Scrum 항목의 영구 링크(가능하면 블록 링크)를 Task에 보관한다. 페이지 링크만 제공되는 경우에는 그 페이지에서 같은 Task URL로 TODO를 식별한다. 단순 재개는 날짜가 바뀌어도 기존 연결을 따른다.

**시작 확인.** 사용자가 특정 Daily 링크를 주면 그 페이지를 우선한다. 새 Task로 착수할 때나 오늘 할 일 누락을 복구할 때는 해당 Daily를 다시 읽고, 본인의 **🎯 오늘 할 일** 영역에 이 Task의 페이지 ID가 들어간 링크나 관계가 있는지 확인한다. 어제 한 일, 참고 링크, Task 본문의 역링크는 이 확인을 대신할 수 없다. 없으면 해당 영역의 기존 항목을 보존하며 Task 페이지 멘션을 넣은 체크박스 하나를 추가한다. 누락 복구 시 Task가 이미 `DONE`이면 체크된 상태로, 진행 중이면 미체크 상태로 맞춘다. 같은 항목이 텍스트로만 있으면 링크를 보완한다. 쓰기 이후 Daily를 다시 읽어 확인한 뒤 연결 완료로 보고한다. 반영되지 않았으면 Task URL을 보존하고 Daily 연결을 미완료로 보고한다.

## Milestone

마일스톤 연결은 선택 사항이다. 신규 Task는 과거 Task나 템플릿의 관계값을 복사하지 않고 기본적으로 비워 둔다. Task 목표가 특정 마일스톤의 산출물이나 완료 기준에 직접 기여할 때만 TaskBoard의 `마일스톤` 관계가 가리키는 Milestones 데이터베이스에서 후보를 조회한다. 후보 페이지에서 다음 세 가지를 모두 확인한 경우에만 연결한다.

- 업무 내용과 해당 마일스톤 범위가 구체적으로 일치한다. 프로젝트명이나 비슷한 제목만으로 판단하지 않는다.
- 마일스톤의 담당자·참여자에 Notion에서 확인한 **내 사용자 ID**가 포함되어 있다.
- 마일스톤의 현재 상태가 **미완료**다. 실제 상태 옵션과 완료 그룹을 기준으로 Done·완료된 후보는 제외한다.

적격 후보를 특정할 수 없으면 빈 관계가 올바른 결과다. 새 Task를 생성한 직후 다시 읽어 자동으로 붙은 관계도 같은 기준으로 확인하고 의도한 값만 남긴다. 기존 Task의 잘못된 연결을 정정해 달라는 요청에서는 해당 Task의 관계만 최소 수정하고 다시 읽어 확인한다. Milestone 페이지 자체의 상태와 다른 Task의 관계는 보존한다.

## Slack과 PR

- 업무가 시작된 Slack 원문이나 사용자가 지정한 스레드 URL을 Task에 남긴다. 관련 URL이 뒤늦게 주어지면 같은 Task에 추가한다.
- 사용자가 이 업무의 PR 생성을 요청하면 기존 PR 템플릿을 유지하고 본문의 `관련 링크`에 Notion Task와 확인된 Slack URL을 넣는다. 사내 링크를 공개 저장소 등 더 넓은 독자에게 노출하는 경우에는 공유 범위를 먼저 확인한다.
- PR 생성 결과 또는 이미 지정된 PR의 실제 URL을 Task에 추가한다. 링크용 속성이 있으면 사용하고, 여러 PR을 담을 수 없는 속성이면 본문에 목록으로 남긴다. 기존 URL·본문은 보존하고 같은 링크는 한 번만 쓴다. 재시도 때는 이미 열린 PR과 작성된 링크를 확인한다.

## 완료와 결론

1. 시작할 때 정한 완료 기준과 실제 결과를 대조한다. PR 제출 자체가 완료 기준이면 제출로 마감할 수 있다. 리뷰·병합·배포가 기준에 포함되면 해당 결과까지 확인한다. 막혔으면 진행 상태와 미체크 TODO를 유지하고 Task에 막힌 지점과 남은 일을 적는다.
2. Task 본문의 **완료 요약**에 팀원이 이해할 수 있도록 한국어로 결론을 쓴다. 무엇이 어떻게 달라졌는지, 무엇으로 확인했는지를 구체적으로 적고, 인계할 일이 있으면 덧붙인다. 조사 업무라면 확인한 원인과 결정한 조치를 남긴다. 예를 들어 “정산 내역을 다시 내려받을 때도 환불 건이 포함됩니다. 누락됐던 2월 사례로 재조회해 화면과 CSV 금액이 일치하는 것을 확인했습니다.” 링크는 관련 링크 영역에 유지한다. 재시도 때는 기존 완료 요약을 갱신한다.
3. 요약 저장 후 Task의 상태를 `DONE`으로 바꾸고, Task에 명시적으로 연결한 각 날짜의 내 Scrum TODO를 완료 처리한다. 블록이면 체크하고 별도 상태 필드가 있으면 기존 완료 값을 사용한다. Task 상태를 표시하는 관계/롤업이면 반영된 값을 확인한다. 날짜가 바뀌었어도 기록해 둔 원래 항목을 사용한다.
4. Task와 Scrum을 다시 읽어 요약·상태·체크를 확인한 뒤, 이 Task가 로컬에 기억된 경우에만 `python3 <스크립트> clear <Task-URL>`로 재개 알림을 해제한다. 사용자에게 결론과 Task URL을 전달한다.

Notion이나 PR 쓰기가 도중에 실패하면 성공한 쪽의 URL과 남은 작업을 알려준다. 재개 시 해당 항목을 읽고 빠진 변경만 적용한다. 생성 응답이 불확실하면 원격 결과를 먼저 대조하고, 식별할 수 없으면 새 항목을 만들지 않는다. Notion MCP가 꺼져 있으면 추적이 보류된 사실을 알리고 독립적으로 수행 가능한 본업은 계속한다.

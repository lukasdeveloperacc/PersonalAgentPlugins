# Conditional E2E review

Use the Planner's connected-flow scenarios and the common independent-review inputs/verdict format in `SKILL.md`. The reviewer inspects the relevant contracts and validates the full observable outcome, rather than treating passing unit tests or a successful page load as E2E evidence. Include the main success path and relevant failure, authorization, or state-transition cases affected by the change. For non-browser service/job flows, use the project's existing permitted API/CLI/integration harness; Chrome DevTools is not a prerequisite.

Tie evidence to the frozen revision and verify that the running build/services represent it. Record scenario, environment/build identity, steps, expected versus observed results, and relevant artifact/log paths. Use screenshots, console/network observations, and persisted state where they prove an acceptance criterion; keep output focused and redact credentials/personal data. Distinguish manual browser validation from automated E2E tests. If the runtime, fixtures, permissions, or a required boundary cannot be verified, report the gap and `BLOCKED`; observed defects require `CHANGES_REQUIRED`. An untested required scenario cannot receive `PASS`.

Remain read-only on product files. Use the approved validation environment and fixtures; coordinate mutable test accounts/data and browser targets through the leader so concurrent reviewers do not invalidate each other's observations. Clean up only test state created by this run. Do not perform live payments, send external messages, or modify production/user data without authorization. Send required fixes to the leader for the owning Executor, then review the new frozen revision.

## Browser selection and MCP lifecycle

The leader owns setup and cleanup; reviewers request browser access through the leader instead of racing to change shared MCP configuration. Enable only the server required for the current browser validation, not the whole MCP catalog. Read only relevant skills/tool schemas and keep observations small to limit context use.

1. **Orca environment:** establish that the task has an available Orca-managed browser context, rather than inferring it from an installed binary. Resolve/load the installed `orca-cli` skill and its version-matched guide and use Orca browser for inspection and interaction. Do not enable Chrome DevTools MCP in this path. A known Orca environment with an access/tooling failure is a recovery issue, not proof that Orca is absent.
2. **No Orca environment:** resolve/load `lukas-plugin:mcp-setup` and use its actual base directory, host (`codex` or `claude`), and canonical script. Run `<mcp-setup-base>/scripts/mcp.sh <host> list`; if `chrome-devtools` is off, run the same script with `enable chrome-devtools`, then verify its configuration status. Record that this run needs Chrome and must disable it afterward, including if it was already on. This basic-team browser workflow authorizes that scoped enable/disable; leave other MCP entries unchanged. Do not use `disable` without the server name.
3. **Connection readiness:** configuration on is not evidence of callable tools. Verify the host exposes usable Chrome DevTools tools and the intended test target before dispatching browser validation. Follow mcp-setup's connection instructions: Codex requires a new session when the tools are absent; Claude requires reconnection. Use supported reconnection when available. Otherwise preserve the progress path, frozen revision, scenarios, and cleanup obligation for resume, report the connection blocker, and do not claim runtime verification. Never replace missing tools with invented calls. If ending the run rather than retaining an explicit pending resume, perform cleanup.
4. **Cleanup:** retain Chrome only while required browser work or review/fix rounds remain. After all required browser validation finishes, or on cancellation/terminal blocker, close only browser targets and clean up test fixtures created by this run before disabling access; do not close the user's tabs or Orca environment. Run `<mcp-setup-base>/scripts/mcp.sh <host> disable chrome-devtools` and verify `list` reports off. Disable even when it was on before this run, as requested for this workflow. If setup or validation fails after enabling, cleanup is still required. Attempt MCP disable even if fixture cleanup fails; report any cleanup failure and resolve it before claiming complete.

Record selected browser, actual tool readiness, scenarios/results/gaps, and MCP cleanup state in the existing progress fields. Removing MCP registration may leave an already connected session's tool definitions visible until reconnect/restart; report configuration off separately from observed disconnection and do not promise an immediate reduction of current-session tokens.

# Reporting contract

Main/root selects the backend and owns the run, including standalone team invocations: run creation, stage, summary, blockers, decisions, reviews, asks and `close_ask_ids`, retro, the lead and published worker cards and the final `완료`/`중단`. In Office mode leads also report their own team's cards ([Lead reports](#lead-reports)); otherwise they send summaries to root. Workers report to their lead. Office is a visibility surface, not the scheduler or an authority grant. Use plain Korean for public progress.

## Select once; resume the same mode

Inspect available tools and actual configuration. Missing tools alone do not prove Office absent. When enabled tools are missing, use supported discovery and the installed `lukas-plugin:mcp-setup` diagnostic guidance; do not change global configuration, install or restart shared services merely to choose a backend. On Claude Code, discovery is `ToolSearch` with `select:mcp__office__report,mcp__office__ask`; a startup `ECONNREFUSED` or one failed `curl` does not settle NOT READY. While NOT READY, repeat that ToolSearch at every checkpoint (each lead spawn or result); as soon as the tools appear, send the initial report before other work.

For enabled-but-unexposed tools, actor/seat display problems or payload readback, read [office-operations.md](office-operations.md). It separates transport readiness, saved report data and visible Office behavior.

| Evidence | Action |
| --- | --- |
| Supported MCP transport advertises `report` and `ask`, initial report succeeds | Select `office`, save returned run ID; create no progress HTML. Ask execution stays unverified until a real decision |
| Office explicitly absent or disabled | Select `html`, use existing progress.py; do not require Office enablement |
| Office configured/enabled/expected but no supported transport exposes the required schemas, or initial report fails | NOT READY: diagnose and recover; never reinterpret as absent |
| Configuration unknown | UNKNOWN: resolve configuration; do not claim a working selected backend |
| Saved mode on resume | Keep mode and existing run ID/page; never create a replacement run |

There is no automatic mid-run Office↔HTML switch, full local snapshot or migration/merge system. A user-requested switch is separate scope. NOT READY/UNKNOWN or an outage need not stop independent product work: use terminal summaries and explicitly say reporting is unsynchronized.

Native tool exposure is not required if the supported configured HTTP MCP transport has recovered both schemas and a successful report. State reporting synchronization and actual question/answer verification separately; never create a fake question to qualify as ready. A later ask failure blocks only its dependent decision while Office mode is retained.

Keep only minimal reconnection metadata at `<project>/docs/inprogress/<task-slug>.office.json`: `mode`, absolute `project_path`, `run_id`/`url` for Office, `page` for HTML, pending ask IDs and IDs awaiting closure. Preserve old `run_id`/`url` files as Office mode; establish and validate their project identity before a write. No tasks/reviews/decisions/full state belong in this sidecar. Existing plans and worker evidence are separate task artifacts, not a replicated tracker.

Write small JSON to a temporary file in the same directory, validate it, then atomically rename over the sidecar. Save mode/run ID only after successful creation. If the creation response is lost, do not blindly create again or claim selection completed: identify the exact run or report unresolved identity. Validate saved project path and run/page identity on resume; mismatch is a blocker for reporting writes, not a reason to create another run.

## Office

Before the first write, inspect advertised tools: if available, read `get_office_rules({})` for `departments`, `owners`, `plan_lane_precedence`, then `get_active_runs({project_path: "<actual absolute workdir>"})`. Its `runs` contains only that project's unended runs with `run_id`, `title`, `stage`, `last_report_at`. Resume this task's saved run; an independent parallel task gets a new run even at the same path. A matching path or recent timestamp alone does not identify this task. Never change project_path to a reports directory to separate runs, close sibling runs, or reuse them automatically. If discovery tools are absent, keep the saved identity or create the explicitly new task's run and disclose that concurrent-run discovery is unavailable; do not require a server upgrade.

Initial `report` uses absolute `project_path`, title, known spec `doc_path` if applicable, and the first progress patch. As soon as creation succeeds, save its identity and tell the user the new title and run link before dispatching further work; their browser may still show a previous run. Every subsequent `report` supplies both `project_path` and saved `run_id`. Use `http://127.0.0.1:4780/#/run/<run_id>` as the local Office link unless the deployed configuration specifies another address. Switch doc_path to the approved plan only after approval.

Show this task's saved run link and identify other active runs found by discovery by title/ID and their last report time; do not change their state. A newly created run's response may include optional `active_runs`: same-project unended run summaries, including itself unless already ended. Exclude the returned `run_id` when identifying siblings; updates to existing runs omit this field. Check it for runs created after the preflight query, without replacing discovery or selecting an identity automatically; absence is not proof that no other run exists. `get_run.last_report_at`, when present, is a saved report timestamp, not agent liveness; reading the run does not refresh it. Do not send these response fields as report arguments. For initial actor reports and owner corrections, inspect [placements](office-operations.md#verify-the-report-at-the-right-level), including when `include_state: false`.

An empty patch is still a write; never use report as a getter. Newer Office (TaskReporter `b8d244b`+) returns `state` (unless you send `include_state: false`) and `ended_at` in each `report` response and advertises a read-only `get_run(run_id)` returning that run's tasks, decisions, reviews, `ended_at` and asks (answered ones too from `d630a90`, the full `state` from `dc807fc`): when `tools/list` has `get_run`, use it for every readback below and skip `/api/state`. Older Office returns only `{run_id, doc_changes}`; then use `GET http://127.0.0.1:4780/api/state` and inspect only the exact project_path/run_id. The observed shape (may change with the deployed version) is `projects[]{path,runs[]}` with run key `id` and tasks at `state.tasks`: `curl -fsS http://127.0.0.1:4780/api/state | jq --arg p "<project_path>" --arg r "<run_id>" '.projects[] | select(.path==$p) | .runs[] | select(.id==$r) | .state.tasks[]? | {id,owner,status,model,effort}'`. Do not output unrelated project data or save the entire response as local state. If neither identity nor prior task/review evidence can be recovered, state what cannot be verified; never invent prior state or PASS verdicts.

Detect features from the advertised `report` input schema in `tools/list` (or the deferred tool schema), never from the version string or a guess: `patch.tasks[].todos` exists from TaskReporter `5a82487`, `check_replies` and the response `checks` from `f2faf2c`, top-level `include_state` from `dc807fc`. Send a field only when the schema lists it. Without `todos`, keep the checklist as `done/total` plus the current item in the note; without `check_replies`, skip check-ins. With `include_state`, send `include_state: false` on every report: the response keeps `run_id`, `ended_at`, `doc_changes`, `checks` and `asks` but drops the full `state`, and `get_run` returns that `state` when you need it. Older strict Office rejects an unadvertised key, and the oldest silently drops it.

For a targeted readback, use `get_run({run_id, task_ids: ["<affected task ID>"]})` only when its advertised input schema supports `task_ids`: pass 1–100 nonempty IDs, not `[]`. Unknown IDs return no matching tasks; use known affected IDs. This limits `tasks`, `state.tasks`, `placements` and task-related checks; the run-level `__retro__` check and run metadata, asks, reviews, decisions and retro remain run-wide. A partial response is not a complete run inventory: do not infer that other cards were deleted or all checks settled. Without support, read the full run and inspect the affected IDs locally. Final closure/TODO/review/check audits use unfiltered `get_run({run_id})`.

### Check-ins

When the response has `checks`, read every pending one after each `report`; Office repeats it in each response until answered, and delivery is not an answer. A check asks one `진행중` task (`task_id`, owner snapshot) why it has not changed for 30 minutes, why its status/note changed without a todo tick for 15 minutes (newer Office) and/or for its missing model/effort, and lists that task's unfinished todo IDs at creation; reread current todos with `get_run`. For each check:

1. Ask the task's actual owner, through its lead when root answers (root reads its own and observed settings directly): current state, blocker, which listed todos are really finished. Do not answer from memory or a guess.
2. Model/effort: run the team-contract actor check (Claude Code or Codex) and put the observed values on that task in the next `patch`. Only when it finds no record for that agent, name what is missing and leave the fields off; never send requested or default values as observed.
3. Send `check_replies: [{check_id, answer}]` as a **top-level report argument** with the saved `run_id`, in the same report as the related patch: one or two factual sentences (state, blocker, next step, settings or why unknown). Filling fields alone does not answer it.

Mark todos done only after the work is verified; an answer is a record, not completion or health. Resending the same answer is safe; a different answer to an answered check is rejected (`conflicting answer`), and a check closed by status/owner change or run end cannot be answered (`check is closed`). Any rejected reply rolls back the whole report, patch included: read `get_run`, drop only that reply and resend the patch. For a missing-settings check on a legacy aggregate, explain that no single agent is represented; other aggregate checks still require real progress/TODO evidence. A root-owned actor card answers with root's own settings. Office re-asks a still-missing value only after 30 minutes.

When the `report` output schema lists `open_todos`, each response names the patched tasks that still have unfinished todos, with `next`, the first one. Compare it with the real work: tick todos already verified in the next patch, and fix todo order or text when `next` is not what the owner is actually doing.

Validation errors, `isError`, wrong run IDs and project mismatches require correcting the cause. For connection errors/timeouts, inspect the cause and attempt one supported discovery/reconnection recovery; retry only with new evidence. Preserve stable task IDs, decision titles and review round/reviewer keys. If still unavailable, keep Office mode, explicitly report unsynchronized progress and continue independent work. Do not mark synchronization successful without a successful response.

Questions requiring the user use `ask(run_id, question, options, recommended)` with 2–4 options. An answered result supplies the answer. A pending result supplies an ask_id: persist it, continue independent work and poll that same ID rather than creating duplicate questions. Office does not notify you when the user answers: call `ask` with that ask_id again at every checkpoint (each lead message or result, each report) and before any wait or turn end until it returns answered. The call returns at once when answered and otherwise holds until the server wait ends. Newer Office (`d630a90`+) holds about 100 seconds, adds `retry_after_sec` to a pending result (0 means call again now) and lists answered asks in every `report` response's `asks`, repeated until the ask is closed: take an answer from there by `ask_id` and skip IDs already handled. Older Office holds up to 295 seconds, and Claude Code moves a call running past 120 seconds to the background, notifying you when it finishes; a pending result there means call again. While it is pending and the user is at the terminal, tell them in one line that a decision waits in the Office, with the run link. If the terminal supplies the answer, use it and queue the ID for closure. Send `close_ask_ids` as a **top-level report argument**, never inside patch; clear closure metadata only after success. An outage may move the conversation to the terminal without changing reporting mode. Close remaining asks on finish/stop when possible, and expose pending synchronization if not.

If doc_changes is nonempty, read the diff and explain its impact; hold only affected work and ask whether to replan (`재계획` / `그대로 진행`). Replan through root-owned Plan lifecycle or record the reason to retain the plan. Do not invent approval questions for routine progress.

For a new user requirement, root reports whether existing work continues or which affected tasks wait, who updates the plan (root or the root-owned planning stage), and the changed TODOs, dependencies and verification scope. Continue unaffected work and reuse its owners. Keep task/TODO IDs and unfinished work; add meaningful new tasks/TODOs rather than erase history or mark displaced work done. A clear authorized addition needs no new permission question. Example: `기존 API 구현은 계속합니다. root가 계획에 선택 피드백을 반영하고 FE-2에 TODO를 추가합니다. FE-3은 API 결과 후 진행하며 선택·재전송 흐름을 검증합니다.` Use existing stage/task/note fields, not new MCP fields.

Report confirmed actor/task start, completion, failure, waiting and owner/model corrections at the next execution checkpoint, before another dependent dispatch or long verification batch. Leads report these transitions as they happen ([Lead reports](#lead-reports)), rather than waiting for the whole team or review wave; root publishes a small patch for the rest and records synchronization success or failure. Do not wait for a user reminder or final reporting. Confirm actual work started before marking it `진행중`; creation alone can leave it `대기중`.

After 30 minutes with no state change, send a summary heartbeat at an execution-loop checkpoint; this is a fallback, not the status-change cadence. Do not create a timer daemon. Long ask calls require an appropriate host timeout (server hold is 100 seconds by default and up to 300 with `ASK_WAIT_MS`; configured Claude MCP_TOOL_TIMEOUT or Codex tool_timeout_sec must exceed it). Diagnose timeout settings without silently modifying global config.

### Lead reports

Root gives each lead the `run_id` and `project_path`. A lead whose host exposes the Office `report` tool reports its own card and its team's worker/reviewer cards the moment a transition happens (actual start, completion, failure, waiting, a verified todo): `include_state: false` and only `patch.tasks[]` entries with `id` plus the changed `status`, `owner`, `model`, `effort`, `note` or `todos` (and `kind` only when advertised). The Reviewer lead marks each reviewer card `진행중` as soon as that reviewer starts. Model/effort come only from the team-contract actor check; when it finds no record, leave them off and tell root. Root publishes worker cards before dispatch. A current-round reviewer card (`R<round>-<K|P|I|E>`), or a worker/fix card of the lead's team still missing when its agent starts, is created by the lead in that report with `id`, `title`, `owner`, `lane`, `status`, `todos`, `after` when known and observed `model`/`effort`; tell root its id, title and lane. Aggregate gates, `PLAN`, `DONE` and lead cards stay root's. Never send stage, summary, blockers, decisions, reviews, `close_ask_ids`, `retro` or another team's task.

Every writer, root included, sends only the fields it changed, so it never overwrites another writer's values. A lead answers `checks` on its team's tasks itself, asking the owner directly, and forwards other checks to root; root answers those only when the lead is gone or no longer reports. On a validation error, fix and resend. When Office is unreachable or the tool is missing, the lead sends the transition to root, which reports it. Each lead message to root says `Office 반영함` or `Office 미반영` for its transitions. HTML mode keeps root the only writer.

### Retro

Root of the run (basic-team, or a standalone team skill) ends every run with a retro: up to three things in this skill's instructions, tools or process that went wrong, for later skill/MCP fixes. Code defects belong to review findings, not here. Send it only when the `report` schema advertises `retro`, as a **top-level report argument** (like `close_ask_ids`) in the report that ends the run (`완료` or `중단`, including a finish task's auto-close):

`retro: [{skill, skill_version, category, evidence, suggestion?}]`

- `skill`: the entry skill the user invoked (`basic-team`, `thegame-basic-team`, `basic-frontend-team`, …); a composed basic-plan-team stage belongs to its root's run, not a retro of its own.
- `skill_version`: plugin version plus installed commit, from the snippet below (`0.1.0+bb590a2`, or `0.1.0` when no commit is found; `unknown` when no version is found).
- `category`: `instruction_gap` (missing/unclear/contradictory instruction), `tool_friction` (MCP/CLI/host tool failed or misled), `user_correction` (the user had to correct the workflow), `review_miss` (a review gate let through what a later step caught), `other`.
- `evidence`: one line of what happened, naming the step, file or tool. `suggestion`: the change you would make, when you have one.

Collect the leads' `스킬 마찰` lines and root's own observations; merge duplicates and keep the three with the clearest evidence. Without concrete evidence send `retro: []`; never send "went well" or generic advice. Office computes review rounds, check-in and ask latency and whether the run stopped itself; do not restate them.

When consulting `get_retros`, `candidate: true` is a review signal for the same skill/category across runs, not proof of a repeated root cause. Read each item's evidence before merging causes. TODOs ticked in a task's closing patch do not by themselves establish late reporting or batching at run end.

If a report response's `checks` asks for a missing retro, do not use `check_replies`: answer with `retro` (or `[]`) and `patch: {}` in the next report; this works on an ended run without reopening it. In HTML mode, or when Office is unavailable, write the same array to `<artifact-dir>/retro.json` and name that path in the final summary.

```sh
p=$(cd "<basic-team-dir>/../.." && pwd); v=$(jq -r .version "$p/.claude-plugin/plugin.json" 2>/dev/null)
s=$([ "$(git -C "$p" rev-parse --show-toplevel 2>/dev/null)" = "$p" ] && git -C "$p" rev-parse --short=7 HEAD || jq -r --arg p "$p" '.plugins[][] | select(.installPath==$p) | .gitCommitSha[:7]' ~/.claude/plugins/installed_plugins.json 2>/dev/null)
echo "${v:-unknown}${v:+${s:++$s}}"
```

## Public payload

Use only the existing schema; see [progress-example.md](progress-example.md). Team tasks summarize meaningful deliverables, with owners such as `frontend-lead`, `backend-lead`, `docs-lead`, `plan-lead`. A short note contains done/total, current work, blocker, next step and detail-artifact path. Paths are evidence references, not guaranteed clickable Office links. Office does not provide a team/worker tree: do not send `team`, `parent` or `report_to` fields.

Before first publishing each actor, resolve its canonical ID, parent lead, host-valid native name, Office owner and requested/observed model/effort from lead evidence. Keep this small mapping in the existing run evidence, not the reconnection sidecar. Include leads as well as leaves when reporting actor settings; do not create placeholder tasks merely to populate seats. Each worker task is a real deliverable and gets its own card: owner `<team>-<short>` (for example `frontend-badge`, seated in that team's room), its own model/effort and todos, `after` its prerequisites. The lead card carries only the lead's settings and coordination todos.

When the `report` input schema advertises `patch.tasks[].kind`, use `kind: "actor"` (also the default when omitted) for a real executor, including root and leads. Use `kind: "aggregate"` only for an approval/coordination gate with no single executor: omit model/effort, leave owner empty, and keep its TODOs and review evidence. An aggregate creates no worker character and is excluded from actor selection; only its missing-model/effort check is exempt, not TODO-stagnation/30-minute checks or completion validation. Do not classify a real worker as aggregate to hide missing settings. Without schema support, omit `kind` and answer any missing-settings check with the gate's actual non-actor reason. See the [Office-only example](progress-example.md#office-only-actor-and-aggregate-cards).

Correct an existing card's kind on the same task ID only when its actual purpose warrants it. An actor↔aggregate transition closes previous pending checks while preserving history and resets that task's observation clock; actor mode restores missing-settings checks. Reread its current checks before replying to an old check ID; do not toggle kind to suppress a real warning.

- `tasks` merge by `id`; `decisions` by `title`; `reviews` by `round` + `reviewer`; `tasks[].todos` (`id`, `text`, `phase`, `done`, `detail`) by todo `id` inside its task, so ticking sends only `{id, done:true}`.
- A missing `done` is unfinished. A task cannot become `완료` while its own todos are unfinished: verify each one, then tick it in the same patch that completes the task. Never add an unfinished todo to a completed task. Add a todo only for work this card will really do; when work moves to another card, tick the old todo only after the new card verifies it, with `detail` naming that card. Both Office (`f2faf2c`+) and progress.py reject these with `task <id>: unfinished TODOs: <ids>`; fix the work, not the checkbox.
- List todos in the order the work will happen; Office shows the first unfinished one as current. Unless the lead already reported them, root ticks the todos each lead result names in `끝낸 TODO` in the next report, never saved up for the task's completion, and adds newly found work as new todos rather than note text.
- Task `note` is one or two short lines of current state and evidence path (Office splits lines on `\n` and ` · `). Checklist items, test counts and explanations belong in todos and their `detail`, not a long task note.
- Decision text is `body`, not `detail`. Newer Office rejects unknown keys at every level and out-of-enum lane/status/reviewer with `Unrecognized key: "<key>" at <path>`; fix that field and resend, do not drop the update. On older Office, compare outgoing keys against the schema and examples yourself: it silently stores unknown nested fields without rendering them.
- Stage begins with `계획`, `구현`, `리뷰`, `수정`, `마무리`, `완료` or `중단`. `중단` means abandoned, not waiting for an answer. Keep current stage while waiting; put the question in todo/blockers.
- Task lane is work kind: `plan`, `build`, `review`, `fix`, `finish`. Task status is `대기중`, `진행중`, `완료`, `중단`; all nonwaiting tasks carry a one-line note. `after` is dependency only.
- Domain reviews are normal `lane: review` tasks with frozen revision, verdict and evidence in note. `reviews.reviewer` accepts only `Karpathy Agent`, `Ponytail Agent`, `Impeccable Agent`, `E2E Agent`.
- For each collected external review result, root sends `patch.reviews[]` with its actual `round`, exact `reviewer`, `verdict` (`PASS`, `CHANGES_REQUIRED` or `BLOCKED`) and `note` at the next reporting checkpoint, alongside any task transition. A completed task or its note alone does not publish the review result. Put readable result content in `reviews[].note`: reviewed revision, verdict rationale, key required/advisory findings or their absence, checked/unchecked scope and evidence path where relevant; a bare PASS, round label or path is insufficient. Keep full logs in the evidence artifact. Verify the saved entry by round/reviewer through `get_run`; this confirms stored content, not screen rendering. Preserve earlier rounds and do not copy their PASS into a new one. An uncollected result stays explicitly `미보고` in progress/gate notes, never an invented verdict; this is not a new verdict enum. Reviewer leads return this content to root and keep their Office writes limited to their own team's tasks.
- `todo` is a user action/decision, or `없음`. Failure/unchecked worker evidence must remain visible in the team summary.
- Put a model/effort on a card only for the actual agent represented. Preserve full requested model ID vs host-confirmed distinction; do not attach worker models to an aggregate gate or fabricate observed settings. The writer (root, or a reporting lead for its team) fills model/effort directly from the team-contract actor check (Claude Code or Codex) and never sends them empty. Mark an agent's card `진행중` in the same patch that carries its observed settings, after its first turn: newer Office asks at once about a working actor card without them. A root-owned card (PLAN, DONE) that goes `진행중` carries root's own observed settings. Aggregate cards and agents the check finds no record for omit both; answer a missing-settings check only if one is actually returned, using the reason. Clear a wrong value with `""` only on a card that is not `진행중` or in the patch that sends the right value; an empty value on a working actor card triggers a check.
- `진행중` describes active execution, not an unresolved approval. A finished review attempt can be `완료` with CHANGES_REQUIRED preserved; the required approval gate remains open until root verifies same-revision PASS. When no represented reviewer is working, the aggregate gate is `대기중` with the completed attempt's verdict in its note; while other reviewers still work, it remains `진행중`. Do not mark a gate complete or abandoned merely to stop a character. Fix tasks depend on completed prerequisites, not their own still-open approval gate.
- The reducer only checks task closure; it does not independently establish review PASS. Close a finish task only after real completion.

Brief the user at plan conclusion, blockers, review-round outcomes and finish: done, remaining, user actions, blockers and link. At finish distinguish product completion from reporting synchronization and unresolved asks.

Before claiming Office is closed, read only the exact run and check open tasks, required final-revision verdicts, pending questions and pending checks. Audit every task's todos, including `중단` tasks: run success (explicit `완료` or the finish task's auto-close) is rejected with `run stage 완료 has unfinished TODOs` while any is unfinished. Finish the real work, or end the run `중단` and report the remaining todos; never tick them to pass. After the final report, verify `ended_at` from the report response and its stage from `get_run` (or the response `state` when present; older Office: `/api/state`). Audit actor settings as confirmed versus unverified, not simply nonempty fields. If a browser tab disappears, preserve any earlier screen evidence and report the final API result separately; do not claim a fresh screen check.

## HTML only when selected initially

Use `<project>/docs/inprogress/<task-slug>-<YYYYMMDD-HHmm>.html`. Initialize once, then send only changed fields via update; resume the saved page. Never initialize HTML because an Office run became unavailable. Run Python skill commands with `uv run`:

```sh
uv run "<basic-team-dir>/scripts/progress.py" init "<page>" --title "<작업 이름>"
uv run "<basic-team-dir>/scripts/progress.py" update "<page>" --input "<patch.json>"
uv run "<basic-team-dir>/scripts/progress.py" status "<page>"
```

The existing helper timestamps tasks and marks completion when a finish task is complete and no tasks remain open. Root must still verify required reviews and final checks. Ask questions in the terminal in HTML mode. Do not add a reporting helper or duplicate state store.

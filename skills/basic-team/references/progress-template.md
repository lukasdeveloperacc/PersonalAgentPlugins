# Populate the progress template

Record timestamps and chronological display follow [progress-updates.md](progress-updates.md). Each record shows `recordedAt`, or `시간 미기록` for legacy entries without a known time.


Use `scripts/progress.py` from the resolved basic-team skill directory to initialize `<executing-project-root>/docs/inprogress/<task-slug>-<YYYYMMDD-HHmmss>-progress.html` from `assets/progress-template.html`. Follow [progress-updates.md](progress-updates.md) for commands, partial updates, save receipts, and resume checkpoints. Run from the target project/worktree root. Reuse the same file when the task continues or resumes, preserve completed runs, and never overwrite another run’s file. It opens via `file://` with no network, build, server, or periodic refresh. The updater preserves its styles, dependency graph, tooltip, accessible detail modal, and tab interaction code; only the embedded `script#progress-data` JSON changes.

## Data

New schema-4 pages use [evidence-progress.md](evidence-progress.md). Evidence and typed task/artifact relationships determine observations and reviews; legacy writable agent status/dependency fields below apply only to schema 1–3.

Unless the user requests another language, write all user-facing data in ELI5-style plain Korean, including summaries, agent reports/tooltips/details, reviews, and decisions/blockers. Lead with what happened, explain what was verified or remains unresolved, then state the next action. Summarize English reports in user-facing explanations; preserve original source-bound evidence bytes unchanged. Use Korean verdict labels such as “통과 / 수정 필요 / 확인 보류” without changing their meaning; preserve superseded results and validation gaps. Keep tool/model names, identifiers, commands, paths, hashes, numbers, and internal graph values unchanged, placing detailed evidence in `meta` or agent details. Keep the first view to current work, completed work, remaining work and blockers, derived from the same evidence-backed task view as the checklist. Flow/graph, model settings, hashes and raw evidence belong in expandable details; retain material gaps there.

- `goal`, `summary`, `stage`: concise goal, plain-language next step, and actual workflow stage. In schema 4, the current/completed/remaining/blocker summary and phase flow derive from the same task view; do not maintain competing manual state summaries. The script owns `updated` (last saved timestamp with timezone), `path`, and `_progress` checkpoint metadata. Do not advance the report timestamp of a silent agent.
- `path`: the progress file's actual absolute path, set by the script. Include the clickable page link and confirmed save time at meaningful checkpoints; keep the absolute path in page details and resume context. Keep the same path throughout the run and label the link with the task name. The page falls back to its own local URL path when omitted; clipboard refusal has a manual-copy message.
- `blockers`: `{ "text": "<observed blocker summary>", "tone": "neutral" }`. Never infer no blockers from silence.
- `flow`: ordered `{ "title": "<stage or lane>", "body": "<tasks, parallel branches and prerequisites>" }` entries. Include only task-relevant areas and required reviewers. Group parallel Frontend/Backend work in the same implementation stage rather than implying sequential execution.
- `plan`, `decisions` (and legacy `reviews`): arrays of `{ "title": "<short heading>", "body": "<facts>", "meta": "<optional revision, time or evidence path>" }`. Plan includes draft/approved revision, work allocation with task IDs/owners/files/dependencies/contracts/acceptance criteria and conditional-review activation reasons. Schema-4 reviews derive from the complete published round; their details include content identity and validation evidence/gaps. For E2E, include scenarios, environment/build identity, expected/observed outcomes and manual versus automated evidence; record browser selection, actual tool readiness and Chrome MCP cleanup state in Decisions. When library documentation checks apply, include the package/version, sources, compatibility findings and remaining uncertainty after all required independent reviews arrive. Decisions also include rationale, blockers, options and unresolved user questions.
- `agents`: allocation/identity cards with stable `id`, `name`, `role`, `area`, `stage`, ownership and model information. Schema 4 derives state/report summaries from source-bound assignments, observations and complete review rounds; do not supply `status`, `tone`, `result`, or `dependsOn` as facts. The default Agent Progress panel lists each registered agent once with its derived three-state status and distinguishes agent count from current task count. The collapsed graph has task nodes, not spawned-agent nodes: sequential implementation, verification and fixes can share one owner. Tasks remain distinct even when one agent owns several. Keep repeated model/time metadata in accessible node details. Requested/invoked/observed model settings stay separate; unknown observations say “미확인”. Hover/focus and accessible dialogs expose source evidence and unknowns.
- `evidence`, `observations`, `assignments`, `artifacts`, `relations`, `reviewRounds`: append-only records described in evidence-progress.md. Relations carry typed task/artifact endpoints; node position or common stage does not create a relationship.
- `handoffs`: append-only stage records (`id`, `transition`, `round`, `revision`, `outcome`, `summary`, `evidence`, `next`, `pending`), stored in this page and read through `handoffs PAGE [--id ID]`. Use [../assets/stage-handoff-template.md](../assets/stage-handoff-template.md); preserve old rounds and reference source evidence instead of duplicating reports. Keep independent verdicts out of these records until all required reviews arrive.
- `reviewNotice`: review collection state in plain language. Keep early independent verdicts and findings out of the HTML's JSON as well as the visible page until all required reviews arrive. Mark superseded verdicts and missing evidence explicitly.
- `taskPlanRevision`, `tasks`: the Planner's Phase TODO snapshot, using the fields in [progress-updates.md](progress-updates.md). The Plan tab groups tasks by Phase and shows checked completion, status, owner, task ID, evidence, and per-Phase/overall completed counts. Checkboxes are read-only report indicators; the leader updates the saved snapshot from actual reports. Display the source plan revision and whether it matches the approval record. No tasks means an honest waiting state. Reopened tasks become unchecked; counts do not claim effort percentages or replace completion gates. The existing native task record remains authoritative for host lifecycle.

Visible task/agent status is only **대기중 / 진행중 / 완료**. Started blocked work stays 진행중 with a short reason; source events, unknown observations and review verdicts are details rather than extra statuses. 완료 requires acceptance evidence, and review completion requires the complete published batch. Approved replaced tasks (`supersededBy`) stay in history outside current counts. Schema-4 status color is derived, never supplied as proof. No node or edge animation represents execution or traffic. Hover/focus may highlight explicit neighbors; color supplements text. Empty arrays show honest waiting/unknown states. Show last observed time separately from save time; a static page cannot detect later filesystem changes. Optional `meta` remains plain text, not executable HTML. Legacy pages retain their original saved renderer and its limitations.

`progress.py` serializes the JSON and escapes `<` itself; never edit the embedded JSON by hand. Rendered report values use `textContent`; preserve that boundary. Keep the remaining template unchanged and save the complete page atomically when practical. Do not insert source HTML, secrets, private reasoning, or unverified claims. Translate fixed UI labels and `lang` when needed without changing tab IDs.

The template is a saved view. It does not start agents, poll, fetch external resources, automatically reload, or replace basic-team's reviewer and final-revision gates.

New pages use a dark screen palette with readable text, status badges, tooltips, and dialogs; printing uses a light palette. Preserve these template colors when populating reports. Updating an existing page keeps that page's saved styles.

## Task and revision graph

Use explicit typed relations only. `prerequisite` means a declared task dependency; `contributes` means a completed task reported scoped outputs present in a frozen artifact; `review_assignment` means the host accepted a reviewer assignment for that artifact; optional `delivery` distinguishes a recorded send from recipient acknowledgement. Each edge exposes its source and limits in accessible text. Desktop shows static routed edges; narrow screens use the relationship text list instead of overlapping SVG lines. No relationship proves exhaustive file reading.

A graph node is a task or frozen artifact, never proof of a newly spawned agent. Label lanes as the assigned role’s tasks; a main-owned grouped review uses its assigned reviewers’ lane. For six Executors and four reviewers, show only supported task contributions → frozen revision → accepted review tasks. Never synthesize 24 Executor/reviewer links. Queued review assignments may be shown as planned nodes without accepted-assignment edges. Missing evidence remains missing; do not invent links to remove a graph warning. Main remains in `flow`, not an agent node. New fix-round assignments/artifacts retain old records as history.

Legacy `dependsOn` is a declared prerequisite only. It must not be interpreted as delivery, review assignment or coverage, and must not be populated with all implementation agents merely to make connected columns. Updates do not replace legacy renderers; their former animation is not new live telemetry.

## Presentation contract

Preserve major-domain Plan / Agent Progress / Reviews & Validation / Decisions & Blockers / Handoffs tabs (localized labels), keyboard controls, visible active tab and selected-tab persistence when local storage is available. Goal, actual stage, current/completed/remaining/blocker summary and confirmed update time stay above tabs. All panels remain in the same standalone HTML file. Keep task names, owners and the three status labels visible. Put the relationship graph, IDs/hashes and each agent's requested/invoked/observed model/effort in expandable details, preserving “미확인” and source evidence. Modal opening/closing must preserve keyboard access and return focus to the node. The page's absolute path and copy control remain visible. Do not replace template presentation on every report.

New pages show saved handoffs in the 인수인계 tab, newest first, with expandable record details. Older pages keep their existing renderer on update; their saved records remain readable with `handoffs PAGE` even when there is no handoff tab. Start a new run to use the current template rather than migrating a continuing run’s renderer.

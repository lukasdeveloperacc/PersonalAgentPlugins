# Basic Team

The main session is the leader and user contact. It dispatches ready work as soon as real prerequisites are met and batches factual reporting; Executors edit product files, strong planning agents make the plan, and independent reviewers assess it. Run the full workflow even for a small task when the user requests this workflow. A request to inspect or edit this skill is not a request to execute it.

Use Codex native collaboration or Claude's installed OMC `team` native-team path in the current main session. Do not launch tmux teams, another leader, or a CLI substitute. Frontend and Backend are work classifications, not a limit of one Executor per area. These review personas do not mean the named people reviewed the code.

## Invariants

- Follow the user's scope, amendments, permissions, budgets, and validation policy. This workflow grants no publishing, pushing, deployment, unrelated changes, or agent/global configuration changes. The scoped browser/MCP exception is specified in [references/e2e-review.md](references/e2e-review.md).
- Preserve the Planner, approved planning review, task ownership/contracts, progress page/receipts, ELI5 briefings, stage handoffs, independent final-revision reviews, validation, and verified host-appropriate lifecycle cleanup. Only a specific user instruction can omit a requirement; record it in Decisions & Blockers and the final compliance table. Missing capability means an honest gap or BLOCKED, not a silent waiver.
- The leader never edits product files. Children do not launch another workflow or write the progress page. Preserve pre-existing user changes and other agents' edits; one named owner per shared file.
- Review all finished implementation/integration edits on one frozen product revision. Every required reviewer must PASS that same final revision; any product edit supersedes earlier verdicts and affected tests. No self-review, elapsed time, timeout, or retry count replaces evidence.
- New pages follow [evidence-backed progress](references/evidence-progress.md): freeze assignments and review scope, capture actual source records, and derive state from evidence. Task dependencies, reported contributions, review assignments and deliveries are different relationships; none proves review coverage or live execution.
- The HTML, handoffs, helper gates, and hook records are reporting/recovery data. They neither establish permission nor replace native task lifecycle, real host settings, or actual validation. Preserve phase-release and final gates, but do not make per-task saves, receipts, or handoff readbacks prerequisites for ready work inside a released phase. Reporting-only failures remain pending while independent authorized work continues.

Missing/rejected required arguments or a known actual mismatch block that child; use supported corrected invocation/recovery, never an unknown-setting exception to pass a known mismatch.

If the user requires proof of actual settings, initialize `strict-observation-v1`: unknown model or effort pauses substantive work unless the user explicitly permits that missing observation for that child. Existing pages without a policy retain strict v1, and resumed runs retain their recorded policy. Never relax a run through `update` or reinterpret an old exception as observation. ## Leader runbook

`<bt>` is this skill's resolved directory. Run `uv run "<bt>/scripts/progress.py" ...` from the target project/worktree root; `PAGE` is an absolute path beneath its `docs/inprogress/`. Never use another Python interpreter. Missing `uv` is BLOCKED.

At kickoff, create one private artifact directory with `mktemp -d /tmp/basic-team-XXXXXX`. Record its exact absolute path as `ARTIFACT_DIR` in the page's Decisions and pass it in every child's Inputs. Store planning drafts, Architect/Critic reviews, file-backed reports, logs, screenshots, helper inputs, and any file-backed leader task record there; do not create a companion artifact folder or reporting MD/JSON files in the worktree. Product files and explicitly assigned project documentation keep their agreed locations. Reuse the recorded directory on resume, including an existing run's original artifact paths; do not relocate active evidence automatically. Keep referenced files unchanged and available after completion: OS cleanup of `/tmp` can break verification/resume and must be disclosed.

Read each stage's directly linked reference when entering it. Gate exit 0 with `ok` means saved-data checks passed; inspect underlying artifacts/host evidence too. Exit 1 gives unmet problem codes and targets: repair only those missing facts or route a blocker. Exit 2 is a command/input failure: read stderr, fix the call, retain pending work. A helper success does not prove the task happened.

The planning order is **Planner → Architect → Critic**; Critic receives Architect evidence. Product reviewers are **independent of one another**. Do not apply product-review isolation to planning consensus. This applies the installed ralplan method through native agents, not OMX/OMC consensus runtime: no `omx ralplan run`, runtime-owned state writes, fabricated runtime gate, or handoff to ultragoal/ralph.

## Briefs and ready-task dispatch

The Planner groups the allocation into Phase TODOs. Save `taskPlanRevision` and the full `tasks` snapshot in the same progress HTML before implementation; match the approved plan and reuse task IDs in briefs/reports. The Plan tab shows per-Phase checklists and completed counts. Visible task/agent states are only **대기중 / 진행중 / 완료**; a blocker is a short reason beside 진행중, while receipt events and review verdicts are details, not extra states. Update statuses from actual reports and validation, require evidence for `done`, and reopen affected tasks when fixes invalidate completion. Publish independent review TODO outcomes only after the full review set is collected. See [progress-updates.md](references/progress-updates.md) for fields; no separate TODO file is needed.

Generate prompts with `brief --role <planner|architect|critic|executor|documentation_executor|reviewer> --input <fields.json>` and call arguments with `spawn-args --host <codex|claude> --role <role>`. Use generated arguments as actual tool arguments, not merely prompt text. Pass generated briefs unchanged; put task detail in their fields. When the approved plan includes documentation work, assign that task to `documentation_executor`; otherwise do not create this role.

Each brief requires `task_id`, `request` including amendments, `project_instructions`, `workdir`, `area`, `owned`, `inputs`, `deliverable`, `validation`, `contacts`, and `skills` (resolved paths). Reviewers additionally need `revision` (the manifest digest) and `reviewer`. In `inputs`, supply the frozen assignment ID and task ID; review inputs also include artifact/manifest identity and every assigned criterion with required/applicable flags and exclusion reasons. Do not invent extra brief arguments. Give read-only roles `owned: none (read-only)`. Architect Inputs contain plan revision/path; Critic Inputs contain that plan and Architect artifact. Executor Inputs contain agreed contracts, prerequisites, existing pattern paths and concrete input/output examples; Deliverable gives observable completion criteria and Validation gives exact allowed commands. The child confirms ownership in its first factual checkpoint and works without a redundant MODEL/leader-release exchange unless strict observation is pending.

Use only these product-review assignments, one agent per activated role (at most four): `karpathy` → `Karpathy Agent`, `ponytail` → `Ponytail Agent`, `impeccable` → `Impeccable Agent`, `e2e` → `E2E Agent`. Use these exact display names in `agents[].name`, reviewer brief `reviewer` fields, task names and reports; keep the lowercase IDs for records. Karpathy/Ponytail are mandatory; Impeccable/E2E retain their activation conditions. Neither the leader nor children may add review helpers, split a reviewer by area, or create a separate synthesis reviewer. Resume the same reviewer for fixes; stop and verify the unavailable reviewer’s active work before creating its replacement, following the host reference; interruption does not free a slot or prove agent termination. Planner/Architect/Critic are separate planning roles, not additional product reviewers. Freeze every assignment before launching, then capture the actual outcome and accepted settings. Keep one structured factual task record with task ID, owner/files, prerequisites, acceptance criteria and observed outcome; use it to populate the HTML instead of rewriting the same facts. Claude still maintains its native task lifecycle; on Codex the structured allocation/evidence record can serve as the leader task record.

Split substantial independent work inside each area as well as across Frontend/Backend; do not manufacture parallelism from tiny edits. Explicitly classify unaffected areas as not needed. Define cross-area inputs, outputs, errors/auth and shared-file owners before release. Dispatch all ready independent tasks within capacity, start dependents when their own prerequisites succeed, and reuse compatible idle Executors for dependent integration, verification and fixes. Allocate agents for useful concurrent file ownership, not one agent per TODO or phase; an integration owner need not be a new agent. A finished task does not necessarily free an agent slot. Assign each feature Executor its related tests as well as product code; give shared fixtures and cross-area tests a named integration owner. Use one existing Executor or activated E2E Agent as the execution owner for each required full-suite command/revision/environment, following workflow-contracts; do not create an extra regression or progress-reporting agent. Keep implementation checks distinct from independent reviewer assignments. Keep progress task names and ownership current when work is reassigned.

## Reviews, validation, and blockers

Load [references/workflow-contracts.md](references/workflow-contracts.md) at review/fix/exit. Divide primary coverage: Karpathy checks requirements, assumptions and cross-area contracts; Ponytail checks implementation, callers, edge cases and simplicity. Both report any correctness/regression issue they encounter without duplicating a full checklist. Give all reviewers the same request, approved plan, criteria, revision and access to the full diff/source and shared validation artifacts; briefs point to those artifacts and each role's targets instead of copying whole files/logs. Each receives only its own review skill and no other verdict/self-approval. Reuse current factual test/browser evidence when it proves the assigned criterion; reviewers independently interpret it and run only missing or affected checks. Give Impeccable its design brief/targets and E2E its scenarios/environment/fixtures/readiness.

Activate Impeccable for visible new/redesigned UI, layout, typography, color, navigation, interaction, responsive behavior or requested design judgment. Internal Frontend refactors without UX impact do not automatically activate it. Activate E2E for connected multi-screen/client-server-persistence/authentication/services/jobs outcomes or requested E2E. File count alone is not a trigger. Save both decisions/reasons and re-evaluate on scope change; never deactivate a reviewer to bypass findings. Read [references/conditional-reviews.md](references/conditional-reviews.md) when these conditions or changed external APIs/dependency versions apply; read [references/e2e-review.md](references/e2e-review.md) only for activated E2E or required browser interaction.

Capture each reviewer’s single structured JSON result unchanged with its actual source identity. Publish the complete frozen assignment batch atomically; derive PASS / CHANGES_REQUIRED / BLOCKED, findings and reported coverage from those source reports, never a separate verdict summary. Until collection completes, keep report bodies, paths, verdicts and criterion outcomes outside ALL page data; only redacted lifecycle receipts and immediate tool blockers may appear. PASS needs met criteria, required validation evidence, and no required finding. Advisory improvements do not expand scope. Resolve conflicting findings against evidence; never overrule an unresolved finding and fabricate PASS.

Planner specifies smallest allowed checks proving acceptance and affected boundaries; preserve required project checks. Record command/action, product revision, environment, exit code, evidence and unchecked scope. Later product edits rerun affected checks and supersede stale evidence. Required failures, including baseline suite failures, prevent all-green completion unless the user explicitly changes acceptance scope. Forbidden/not-run checks are gaps, never passes.

For a blocker: identify affected task/failure → bounded code/config/docs/log investigation → smallest already-authorized remedy within ownership → verify/report. Reviewers stay read-only. Ask through the leader only for materially different unresolved outcomes, missing requirements/access, or needed authority; include evidence, recommendation and tradeoffs. Save the question/owner, pause dependent work, continue independent work, and resume once the real answer arrives. Silence is not approval; no repeated failed retries without new evidence.

## Checkpoints, briefings, and exit

The main session is the sole semantic page writer. Use one standalone HTML page `<project-root>/docs/inprogress/<task-slug>-<YYYYMMDD-HHmmss>-progress.html`, unique at kickoff and reused through fixes/resume/compaction. Never put this HTML page in the plugin directory or silently fall back to `/tmp`; supporting artifacts use `ARTIFACT_DIR` above. Keep the progress page out of product commits unless requested. Preserve accessible tabs/details, inline assets, honest empty states and reduced-motion behavior; keep the relationship graph and technical metadata in expandable details as specified in [references/progress-template.md](references/progress-template.md).

Use easy Korean ELI5 explanations unless the user asks otherwise: what happened → confirmed result/remaining work → next action. Preserve technical facts and unknowns. Brief at kickoff, after planning, consequential decisions/blockers, review rounds, resume, and completion. Keep routine briefings to current work, completed work, remaining work and any blocker, plus the clickable page link and confirmed save time. Put artifact identities, model settings and hook request/confirmation details in the page and final compliance report; mention a material gap when it changes the next action. No new facts means reuse the receipt without another save.

Advance by **received facts → dispatch ready work → batch checkpoint** within a released phase. Deduplicate dispatch independently from save acknowledgement so a failed save cannot repeat a call. Preserve pending patches, and save/check the required phase gate before changing phases; final completion still requires a confirmed save. Do not poll agents/files/mailboxes/capacity, send repeated status queries, or rewrite the page on a timer. When no ready work remains, use supported notification/event wait; timeout is neither success nor failure. Status inspection is limited to initial routing, explicit user request, real failure diagnosis or required lifecycle verification. Host-specific message/resume rules are in the current host reference.

Append stage handoff records to the same HTML page’s `handoffs` JSON array using [assets/stage-handoff-template.md](assets/stage-handoff-template.md), including completion and fix rounds. Include the handoff in the phase checkpoint and check it with the phase gate; read back with `handoffs PAGE --id ID` only for resume or a concrete recovery need. Do not create a separate MD per transition; reference an existing artifact when the user or host explicitly requires one. Resume using the exact saved path, last receipt, policy, pending patches and outstanding IDs; reconcile `status` with actual host/repository evidence. Never select the newest page or treat saved stage as execution authority.

Hooks default silent. Only Main executing this workflow arms after page creation/verification, rearms on continuing requests/resume, retains exact run_id, and disarms on completion/cancellation/failure/task switch. Missing host identity/confirmation uses manual checkpoints. Do not arm when discussing or editing the skill. Commands and confirmation limits are in the current host reference and progress updates.

After final readiness, perform scoped host-appropriate cleanup once; timeout/unresponsive agent recovery and inactive-state evidence follow the current host. Codex task-quiescence may satisfy work completion without proving agent disposal; report those separately. Never stop unrelated agents, delete state to hide workers, or claim unverified exit. Save final outcome, settings, reviews/checks/gaps, shutdown/cleanup, handoff and receipt before the complete gate. Every final report, including BLOCKED/cancelled, includes `compliance PAGE`'s table (`함 / 부분 / 안 함`) with concrete evidence, inapplicable reasons and explicit omissions. Use `complete` only after all required implementation, reviews, validation, saves and lifecycle checks succeed.

01

제품 정의

PersonalAgentPlugins는 한 사람의 AI 코딩 에이전트 환경 — 스킬과 설정 — 을 담아 어느 머신에서든 복원하는 공개 저장소다.

해결하는 문제

여러 AI 코딩 도구를 병행하고 여러 머신을 오가는 개발자는 구조적으로 세 가지 비용을 반복해서 낸다.

  • 중복 저작 — 도구마다 스킬을 따로 두면 같은 내용을 여러 벌 쓰게 되고, 한쪽을 고치면 나머지가 조용히 낡는다. 비용은 도구 수에 비례해 늘어난다.
  • 휘발 — 머신을 옮기면 스킬은 기억에 의존해 다시 쓰고, 설정은 처음부터 다시 만든다. 축적이 되지 않는다.
  • 추격 — 새 에이전트 도구가 계속 등장한다. 지원 목록을 사람이 관리하면 도구가 늘 때마다 손이 간다.

해법의 요지

스킬 내용은 이미 도구 간에 거의 호환된다 — 확인된 모든 런타임이 SKILL.md(YAML frontmatter + 마크다운)를 읽는다. 갈리는 것은 포장뿐이다. 따라서 내용은 한 벌만 두고 포장을 얇은 층으로 분리하면, 도구가 늘어도 저장소는 그대로 있을 수 있다. 설정은 매니페스트로 전달되지 않으므로 별도의 부트스트랩 층이 맡는다.

이 문서의 역할

무엇을 만들지, 무엇을 만들지 않을지, 구조가 왜 이런지, 그리고 이 저장소를 어떻게 늘려갈지를 정의한다. 스킬을 추가하거나 새 런타임을 받아들이기 전에 11장을, 구조를 바꾸기 전에 4장과 15장을 먼저 읽는다.

02

목표와 비목표

목표

  1. G1새 머신에서 두 줄로 복원클론과 부트스트랩 명령만으로 스킬과 설정이 자리를 잡는다. 사전 인증이나 키 발급 없이 시작할 수 있어야 한다.
  2. G2스킬은 한 번만 작성skills/<name>/SKILL.md 하나가 정본이고 모든 런타임이 그 파일을 읽는다. 런타임별 사본을 만들지 않는다.
  3. G3감지되는 모든 런타임에 설치지원 목록을 저장소가 소유하지 않는다. 설치 시점에 그 머신에 실제로 있는 에이전트를 찾아 거기에만 설치한다.
  4. G4공개 저장소로 유지인증 없이 어디서나 클론·설치할 수 있어야 한다. 그 대가로 비밀이 구조적으로 들어갈 수 없게 만든다.
  5. G5새 런타임에 무개정 대응새 도구가 SKILL.md 규약을 따르면 저장소를 고치지 않고도 커버된다.

비목표

범위를 지키는 것이 이 제품의 유지보수성을 결정한다. 아래는 의도적으로 하지 않는 것이며, 하고 싶어질 때 이 항목을 근거로 거절한다.

  1. NG1범용 dotfiles셸, git, 터미널 설정은 범위 밖이다. AI 에이전트 환경만 다룬다. 경계를 넓히면 부트스트랩의 실패 반경이 머신 전체로 커진다.
  2. NG2팀 배포·다중 사용자사용자는 한 명이다. 권한 모델, 조직 정책, 승인 흐름을 설계하지 않는다.
  3. NG3설치본에서 저장소로의 역동기화설치본은 읽기 전용 캐시다. 수정은 항상 저장소 클론에서 하고 update로 받는다. 양방향을 허용하는 순간 "어느 쪽이 최신인가" 문제가 영구히 따라붙는다.
  4. NG4자격증명 보관·배포토큰, API 키, 인증 파일은 저장소가 다루지 않는다. 참조만 하고 값은 환경에서 온다.
  5. NG5런타임 기능의 재구현특정 도구의 오케스트레이션·하니스·에이전트 실행 로직을 저장소가 떠안지 않는다. 이 저장소는 배포 계층이지 런타임이 아니다. 그런 로직이 필요하면 스킬 한 개의 내용으로 들어와야 한다.

04

설계 원칙

구조를 바꾸려는 제안은 이 여섯 항목에 비추어 판단한다. 원칙과 충돌하는 편의는 채택하지 않는다.

  1. DP1콘텐츠와 포장을 분리한다런타임이 바뀌어도 SKILL.md는 바뀌지 않는다. 런타임 차이는 얇은 매니페스트 한 겹이 흡수한다. 매니페스트가 두꺼워지고 있다면 설계가 잘못되고 있다는 신호다.
  2. DP2스킬 폴더는 자체 완결 단위다참조 문서, 스크립트, 템플릿, 런타임별 프로파일은 전부 그 스킬 폴더 안에 산다. 폴더를 통째로 다른 저장소에 옮겨도 동작해야 한다. 공용 디렉토리에 부속 파일을 두면 스킬을 떼어낼 수 없게 된다.
  3. DP3런타임 목록을 소유하지 않는다"어떤 도구가 설치돼 있는가"는 머신의 사실이지 저장소의 사실이 아니다. 감지에 위임한다.
  4. DP4비밀 없음을 규율이 아니라 구조로 만든다"조심해서 커밋한다"는 반드시 실패한다. 저장소에 값이 들어갈 자리 자체가 없어야 하고, 자동 게이트가 이를 강제한다.
  5. DP5설치본은 읽기 전용이다진실은 항상 저장소에 있다. 설치된 사본을 고치는 흐름을 만들지 않으면 동기화 문제가 애초에 발생하지 않는다.
  6. DP6되돌릴 수 있게 바꾼다부트스트랩은 기존 설정을 덮기 전에 백업하고, 무엇을 바꿀지 먼저 보여준다. 두 번 실행해도 결과가 같다.
05

아키텍처

세 겹으로 나눈다. 위로 갈수록 오래 살고, 아래로 갈수록 런타임 사정에 가깝다. 변경은 항상 아래층에서 흡수하고 위층을 지킨다.

L1 정본

플랫폼 중립 콘텐츠

skills/<name>/SKILL.md, agents/*.md, commands/*.md. 사람이 쓰고 읽는 유일한 층이다. 확인된 모든 런타임이 공유하는 최소 공통 형식만 쓴다 — 특정 런타임에만 있는 문법에 의존하지 않는다.

L2 포장

매니페스트 — 얇은 배포 계약

.claude-plugin/marketplace.json 하나가 Claude Code와 Codex를 동시에 커버한다. 내용을 복제하지 않고 source: "./" + 경로 배열로 skills/를 목적별 번들로 잘라 노출할 뿐이다.

claude plugin marketplace addcodex plugin marketplace add
L3 배치

부트스트랩 — 머신에 실제로 놓기

마켓플레이스 개념이 없는 런타임과, 매니페스트로는 전달되지 않는 설정을 담당한다. 런타임 감지 → 스킬 설치 → 설정 템플릿 배치 → 백업 순으로 동작한다.

bootstrap.shskills CLIconfig/ 템플릿
L2를 하나로 합칠 수 있는 근거

Codex CLI가 Claude 형식 매니페스트를 그대로 읽고, 설치 시 자기 형식의 매니페스트를 자동 생성한다. 즉 런타임 간 변환 계층이 이미 런타임 쪽에 존재하므로 저장소가 그것을 떠안을 필요가 없다. 실측 결과는 15장에 있다.

06

저장소 구조

저장소 루트가 곧 마켓플레이스 루트다. 런타임별 하위 디렉토리를 두지 않는다 — 그렇게 나누는 순간 G2가 깨진다.

PersonalAgentPlugins/
├─ .claude-plugin/marketplace.json   Claude + Codex 공용 진입점 (L2)
├─ skills/                           ← 정본. 사람이 쓰는 유일한 곳 (L1)
│  ├─ <skill-name>/
│  │  ├─ SKILL.md                    모든 런타임 공용
│  │  ├─ reference/                  참조 문서 — 폴더 안에 동봉 (DP2)
│  │  ├─ scripts/                    스킬이 실행하는 스크립트
│  │  └─ agents/openai.yaml          런타임별 사이드카. 타 런타임은 무시
│  └─ ...
├─ agents/*.md                       서브에이전트 정의
├─ commands/*.md                     슬래시 커맨드
├─ config/                           ← 설정 템플릿 (L3). 값이 아니라 형태만
│  ├─ claude/settings.json.tmpl
│  ├─ claude/CLAUDE.md
│  ├─ codex/config.toml.tmpl
│  ├─ codex/AGENTS.md
│  └─ shared/mcp-servers.json.tmpl   비밀은 ${ENV_VAR} 자리표시자로만
├─ bootstrap.sh                      감지 → 설치 → 설정 배치 → 백업
├─ scripts/validate.sh               매니페스트 + frontmatter + 비밀 스캔
├─ .github/workflows/ci.yml
└─ README.md

07

런타임 지원 정책

런타임을 두 등급으로 나눈다. G3에 따라 감지 대상 목록은 저장소가 소유하지 않으므로, 아래 표에서 관리하는 것은 1급뿐이다.

등급정의받는 것보장
1급 스킬 로딩과 설정 병합 의미를 모두 검증한 런타임 스킬 + 에이전트 + 커맨드 + 설정 릴리스마다 실설치 스모크 테스트
감지 설치 도구가 그 머신에서 찾아낸 나머지 전부 스킬만 없음. 동작하면 보너스
감지 런타임에 설정을 배치하지 않는 이유

설정 파일 형식이 런타임마다 다르고(JSON · TOML · YAML) 병합 의미도 다르다. 검증하지 않은 런타임의 설정을 건드리면 그 도구를 망가뜨릴 위험이 얻는 이익보다 크다. 스킬은 파일을 추가할 뿐이라 되돌리기 쉽지만, 설정은 기존 상태를 덮는다.

현재 1급 런타임

런타임스킬 전달 경로설정 대상
Claude Code
~/.claude		마켓플레이스settings.json, CLAUDE.md, hooks, .mcp.json
Codex CLI
~/.codex		동일 매니페스트 재사용config.toml, AGENTS.md, hooks.json
Hermes
~/.hermes		skills CLI · 심링크config.yaml
공용 .agents
~/.agents/skills		정본 설치 지점 — 런타임별 심링크의 원본해당 없음

1급 승격 절차

  1. 감지 대상으로 스킬만 배포한 상태에서 실제로 스킬이 로드되는지 확인한다.
  2. 그 런타임의 설정 파일 형식과 병합 의미를 파악한다 — 배열은 덮어쓰는가 이어붙이는가, 주석이 보존되는가.
  3. 설정 템플릿을 config/<runtime>/에 추가하고 백업·드라이런·되돌리기를 검증한다.
  4. 스모크 테스트에 편입하고 이 문서의 1급 표를 갱신한다.

세 번째 단계를 통과하지 못하면 승격하지 않는다. 감지 등급으로 남는 것은 실패가 아니라 정상 상태다.

비밀 취급 원칙

공개 저장소와 설정 복원을 동시에 하기로 한 결정이 이 제품의 가장 큰 제약을 만든다. 설정 파일은 원래 비밀이 모이는 곳이다. 따라서 경계를 문서가 아니라 구조로 긋는다(DP4).

구분내용형태
포함설정의 형태 — 어떤 hook을 어떤 이벤트에 걸지, 어떤 MCP 서버를 어떤 명령으로 띄울지, 어떤 권한을 허용할지*.tmpl 템플릿
포함비밀이 필요한 자리와 그 이름${TAVILY_API_KEY}
제외토큰·API 키·인증 파일의 실제 값환경변수 또는 OS 키체인
제외회사 내부 호스트명, 고객사명, 사내 경로가 박힌 스킬별도 private 저장소로 분리
제외세션 로그·히스토리·캐시.gitignore

강제 수단

  • 템플릿 전용 — config/에는 .tmpl만 커밋한다. 해석된 실값 파일은 .gitignore가 막는다.
  • CI 비밀 스캔 — 모든 푸시에서 스캔하고 발견 시 실패시킨다(FR-7).
  • 부트스트랩의 비침습 규칙 — 병합 시 기존 파일의 비밀 필드는 읽지도 쓰지도 않는다. 자리표시자가 해석되지 않으면 그 항목을 건너뛰고 사용자에게 알린다.
  • 사고 대응 — 실수로 커밋한 경우 히스토리 재작성이 아니라 즉시 키 회전이 1순위다. 공개 저장소에 올라간 값은 이미 유출된 것으로 간주한다.

유지보수 규약

이 장이 일상 작업의 기준이다. 아래 절차를 벗어나는 변경은 4장의 원칙에 비추어 정당화되어야 한다.

스킬 추가

  1. skills/<name>/SKILL.md를 만들고 frontmatter에 name과 description을 쓴다.
  2. 참조 문서·스크립트·런타임 사이드카를 같은 폴더 안에 넣는다(DP2). 공용 디렉토리를 새로 만들지 않는다.
  3. 번들에 배정한다 — 새 번들을 만들지, 기존 번들에 넣을지는 아래 경계 규칙을 따른다.
  4. 검증을 돌리고, 컨텍스트 비용을 확인한 뒤 커밋한다.

번들 경계 규칙

  • 목적으로 나눈다. 기획용, 일상용, 특정 도메인용 — 함께 켜고 끄고 싶은 단위가 번들이다.
  • 런타임으로 나누지 않는다. 그것이 G2를 깨는 가장 흔한 방식이다.
  • always-on 비용으로 나눈다. 항상 켜둘 스킬과 가끔만 필요한 스킬은 다른 번들에 둔다. 그래야 여정 D에서 필요한 것만 설치할 수 있다.

description 작성

스킬의 실효 품질은 본문보다 description이 좌우한다 — 그것이 트리거이기 때문이다. 언제 쓰는지를 사용자의 표현으로 쓰고, 무엇을 하는지만 쓰지 않는다. 겹치는 스킬이 여럿이면 서로를 배제하는 조건까지 적는다.

컨텍스트 예산 관리

설치된 스킬은 모두 always-on 비용을 낸다. 번들을 늘리기 전에 컴포넌트 인벤토리와 예상 토큰 비용을 확인하고, NFR-6 상한을 넘기면 번들을 쪼갠다. 스킬을 늘리는 것보다 안 쓰는 스킬을 지우는 것이 대개 더 큰 개선이다.

릴리스 전 검증

  1. 매니페스트 — 스키마 검증을 strict 모드로 통과한다.
  2. frontmatter — 모든 SKILL.md에 name·description이 있고 이름이 폴더명과 일치한다.
  3. 비밀 스캔 — 전체 트리에서 0건.
  4. 실설치 스모크 — 1급 런타임 각각에서 marketplace add → install → 컴포넌트 인벤토리 확인 → 정리까지 수행한다. 정리를 빠뜨리면 다음 실행이 오염된다.

변경 반영

설치본은 읽기 전용이므로(DP5·NG3), 수정은 저장소에 push한 뒤 각 머신에서 런타임의 update로 받는다. 설치본을 직접 고쳐 문제를 해결하는 습관이 생기면 이 제품의 전제가 무너진다.

이 문서의 유지

다음 경우에 이 문서를 함께 고친다 — 1급 런타임이 늘거나 줄 때(7장), 원칙과 충돌하는 결정을 내릴 때(4장), 런타임 전제가 실측으로 뒤집힐 때(15장), 미해결 질문이 해소될 때(16장).

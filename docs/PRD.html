01

배경과 문제

이 저장소는 원래 Claude용 플러그인과 Codex companion 플러그인을 각각 claude/, codex/ 아래에 두는 구조였다. 재설계를 위해 20fdc78에서 트리를 비웠고, 이전 내용은 902ec25에 남아 있다. 다시 채우기 전에 실제로 무엇이 문제였는지 정리한다.

P1 — 같은 스킬을 두 번 관리했다

런타임별로 디렉토리를 나눈 결과, 내용이 거의 같은 SKILL.md가 claude/와 codex/ 양쪽에 존재했다. 한쪽을 고치면 다른 쪽이 조용히 낡는다. 런타임이 하나 늘 때마다 관리 부담이 선형으로 증가한다.

P2 — 마켓플레이스가 특정 머신의 절대경로에 묶여 있다

현재 등록 상태는 Directory (/Users/chaejin/Desktop/lukas/myGit/PersonalAgentPlugins/claude)다. 이 머신, 이 경로에서만 동작하므로 "다른 곳에서 import"라는 원래 의도가 성립하지 않는다. 실제로 같은 저장소의 클론이 ~/Desktop/lukas/myGit/와 ~/orca/ 두 곳에 존재하며 이미 상태가 갈라져 있다.

P3 — 설정은 어디에도 백업되지 않는다

스킬이 복원되어도 settings.json, config.toml, hooks, MCP 서버 정의, CLAUDE.md·AGENTS.md가 없으면 "내 환경"이 되지 않는다. 새 머신에서는 이 부분이 전부 수작업이다.

P4 — 런타임이 계속 늘어난다

이 머신 한 대에만 스킬 디렉토리를 가진 런타임이 6개 있다 — claude, codex, hermes, grok, factory, 그리고 공용 .agents. 지원 목록을 저장소에 하드코딩하면 새 도구가 나올 때마다 저장소를 고쳐야 한다.

02

목표와 비목표

목표

  1. G1새 머신에서 두 줄로 복원클론과 부트스트랩 명령만으로 스킬과 설정이 자리를 잡는다. 사전 인증·키 발급 없이 시작할 수 있어야 한다.
  2. G2스킬은 한 번만 작성skills/<name>/SKILL.md 하나가 정본이고, 모든 런타임이 그 파일을 읽는다. 런타임별 사본을 만들지 않는다.
  3. G3감지되는 모든 런타임에 설치지원 목록을 저장소가 소유하지 않는다. 설치 시점에 그 머신에 실제로 있는 에이전트를 찾아 거기에만 설치한다.
  4. G4공개 저장소로 유지인증 없이 어디서나 클론·설치할 수 있어야 한다. 그 대가로 비밀이 구조적으로 들어갈 수 없게 만든다.
  5. G5새 런타임에 무개정 대응새 도구가 SKILL.md 규약을 따르면 저장소 수정 없이 커버된다.

비목표

  1. NG1범용 dotfileszsh, git, 터미널 설정은 범위 밖이다. AI 에이전트 환경만 다룬다.
  2. NG2팀 배포·다중 사용자사용자는 한 명이다. 권한 모델, 조직 정책, 승인 흐름을 설계하지 않는다.
  3. NG3설치본 → 저장소 역동기화마켓플레이스 설치본은 읽기 전용 캐시로 취급한다. 수정은 항상 저장소 클론에서 하고 update로 받는다.
  4. NG4자격증명 보관·배포토큰, API 키, auth.json류는 저장소가 다루지 않는다. 참조만 하고 값은 환경에서 온다.
  5. NG5이전 하니스 루프 복원cmux 기반 멀티 에이전트 하니스는 이 저장소의 존재 이유가 아니다. 필요하면 나중에 스킬 하나로 다시 들어올 수 있다.
03

사용자와 여정

사용자는 한 명 — 회사 머신, 집 머신, 원격 VM, 일회성 클라우드 샌드박스를 오가며 여러 AI 코딩 도구를 병행해 쓰는 개발자다. 아래 네 여정 중 A가 이 제품의 존재 이유이고, 나머지는 A를 지속 가능하게 만든다.

여정상황지금목표 상태
A 새 머신 온보딩
방금 받은 노트북, 갓 띄운 VM		 스킬을 기억에 의존해 재작성하고, 설정은 처음부터 다시 만든다. 사실상 복원 불가. 클론 → 부트스트랩 두 줄. 감지된 모든 런타임에 스킬과 설정이 배치된다.
B 스킬 추가·수정 어느 런타임 디렉토리에 넣을지부터 고민하고, 결국 양쪽에 복사한다. skills/ 아래 폴더 하나를 만들고 커밋. 배포는 매니페스트가 알아서 한다.
C 기존 머신 갱신 로컬 경로 마켓플레이스라 클론을 직접 git pull해야 하고, 클론이 여러 개면 갈라진다. 런타임의 update 명령 한 번. 저장소 클론이 없어도 된다.
D 일회성 샌드박스
30분 뒤 버릴 환경		 설정 자체를 포기하고 맨손으로 쓴다. 스킬만 골라 임시 설치하거나, 설치 없이 원문을 참조한다.
04

설계 원칙

  1. DP1콘텐츠와 포장을 분리한다런타임이 바뀌어도 SKILL.md는 바뀌지 않는다. 런타임 차이는 얇은 매니페스트 한 겹이 흡수한다. 매니페스트가 두꺼워진다면 설계가 잘못된 것이다.
  2. DP2스킬 폴더는 자체 완결 단위다참조 문서, 스크립트, 템플릿, 런타임별 프로파일은 전부 그 스킬 폴더 안에 산다. 폴더를 통째로 옮겨도 동작해야 한다. 이전 구조가 contracts/와 templates/를 플러그인 루트에 두어 스킬만 떼어낼 수 없었던 것이 반례다.
  3. DP3런타임 목록을 소유하지 않는다"어떤 도구가 설치돼 있는가"는 머신의 사실이지 저장소의 사실이 아니다. 감지에 위임한다.
  4. DP4비밀 없음을 규율이 아니라 구조로 만든다"조심해서 커밋한다"는 실패한다. 저장소에는 값이 들어갈 자리 자체가 없어야 하고, 자동 게이트가 이를 강제한다.
  5. DP5설치본은 읽기 전용이다진실은 항상 저장소에 있다. 설치된 사본을 고치는 흐름을 만들지 않으면 "어느 쪽이 최신인가" 문제가 애초에 생기지 않는다.
  6. DP6되돌릴 수 있게 바꾼다부트스트랩은 기존 설정을 덮기 전에 백업하고, 무엇을 바꿀지 먼저 보여준다. 두 번 실행해도 결과가 같다.
05

아키텍처

세 겹으로 나눈다. 아래로 갈수록 런타임에 가까워지고, 위로 갈수록 오래 산다.

L1 정본

플랫폼 중립 콘텐츠

skills/<name>/SKILL.md, agents/*.md, commands/*.md. 사람이 쓰고 읽는 유일한 층이다. YAML frontmatter(name, description) + 마크다운 본문이라는, 확인된 모든 런타임이 공유하는 최소 공통 형식을 쓴다.

L2 포장

매니페스트 — 얇은 배포 계약

.claude-plugin/marketplace.json 하나가 Claude Code와 Codex를 동시에 커버한다. 내용을 복제하지 않고 source: "./" + 경로 배열로 skills/를 여러 번들로 잘라 노출할 뿐이다.

claude plugin marketplace addcodex plugin marketplace add
L3 배치

부트스트랩 — 머신에 실제로 놓기

마켓플레이스 개념이 없는 런타임과, 매니페스트로는 전달되지 않는 설정을 담당한다. 런타임 감지 → 스킬 설치 → 설정 템플릿 배치 → 백업 순으로 동작한다.

bootstrap.shnpx skills addconfig/ 템플릿
이 구조가 성립하는 핵심 근거

Codex CLI가 Claude 형식 매니페스트를 그대로 읽는다는 사실이 L2를 하나로 합칠 수 있게 한다. 추정이 아니라 이 머신에서 확인한 동작이다 — codex plugin list가 claude-plugins-official과 omc 마켓플레이스를 각자의 .claude-plugin/marketplace.json 경로로 해석하고 있다. 자세한 근거는 15장.

06

저장소 구조

저장소 루트가 곧 마켓플레이스 루트다. 런타임별 하위 디렉토리를 두지 않는다.

PersonalAgentPlugins/
├─ .claude-plugin/marketplace.json   Claude + Codex 공용 진입점 (L2)
├─ skills/                           ← 정본. 사람이 쓰는 유일한 곳 (L1)
│  ├─ <skill-name>/
│  │  ├─ SKILL.md                    모든 런타임 공용
│  │  ├─ reference/                  참조 문서 — 폴더 안에 동봉 (DP2)
│  │  ├─ scripts/                    스킬이 실행하는 스크립트
│  │  └─ agents/openai.yaml          Codex 전용 프로파일. 타 런타임은 무시
│  └─ ...
├─ agents/*.md                       서브에이전트 정의
├─ commands/*.md                     슬래시 커맨드
├─ config/                           ← 설정 템플릿 (L3). 값이 아니라 형태만
│  ├─ claude/settings.json.tmpl
│  ├─ claude/CLAUDE.md
│  ├─ codex/config.toml.tmpl
│  ├─ codex/AGENTS.md
│  └─ shared/mcp-servers.json.tmpl   비밀은 ${ENV_VAR} 자리표시자로만
├─ bootstrap.sh                      감지 → 설치 → 설정 배치 → 백업
├─ scripts/validate.sh               매니페스트 + frontmatter + 비밀 스캔
├─ .github/workflows/ci.yml
└─ README.md

매니페스트가 하는 일의 전부

하나의 skills/를 목적별 번들로 잘라 파는 것뿐이다. 번들마다 plugin.json을 따로 둘 필요가 없다.

{
  "$schema": "https://anthropic.com/claude-code/marketplace.schema.json",
  "name": "personal-agent-plugins",
  "description": "개인용 스킬·설정 모음",
  "owner": { "name": "chaejin" },
  "plugins": [
    {
      "name": "planning",
      "description": "기획·인터뷰·PRD 작성 스킬 묶음",
      "source": "./",
      "skills":   ["./skills/socrates"],
      "agents":   ["./agents/document-specialist.md"],
      "commands": ["./commands/socrates.md"]
    },
    {
      "name": "everyday",
      "description": "매일 쓰는 범용 스킬",
      "source": "./",
      "skills": ["./skills/code-review", "./skills/deepsearch"]
    }
  ]
}

번들 경계는 목적으로 나눈다(기획용 / 일상용 / 도메인용). 런타임으로 나누지 않는다 — 그것이 이전 구조의 실수였다.

07

런타임 지원 매트릭스

런타임을 1급(보장하고 테스트한다)과 감지 대상(감지되면 설치하되 보장하지 않는다)으로 나눈다. G3에 따라 감지 대상 목록은 저장소가 소유하지 않는다.

런타임등급스킬 전달 경로설정 배치검증
Claude Code
~/.claude		 1급 마켓플레이스 (.claude-plugin) settings.json, CLAUDE.md, hooks, .mcp.json 확인됨
Codex CLI
~/.codex		 1급 동일 매니페스트 재사용 config.toml, AGENTS.md, hooks.json 확인됨
Hermes
~/.hermes		 1급 skills CLI / 심링크 — 마켓플레이스 없음 config.yaml 부분
공용 .agents
~/.agents/skills		 1급 정본 설치 지점. 런타임별 심링크의 원본 해당 없음 확인됨
grok · factory
~/.grok · ~/.factory		 감지 skills CLI 감지에 위임 미지원 미검증
그 외 신규 도구 감지 skills CLI가 인식하면 자동 포함 미지원 해당 없음
설계 결정

설정 배치는 1급 런타임 3개로 제한한다. 설정 파일 형식이 런타임마다 다르고(JSON / TOML / YAML) 병합 의미도 달라, 검증하지 않은 런타임의 설정을 건드리면 그 도구를 망가뜨릴 위험이 실이익보다 크다. 감지 대상 런타임은 스킬만 받는다.

09

비기능 요구사항

ID항목기준
NFR-1온보딩 시간새 머신에서 클론부터 사용 가능까지 10분 이내. 사전 인증 0회.
NFR-2저장소 크기클론 20MB 이하. 바이너리·대용량 에셋 금지. 스킬은 텍스트다.
NFR-3런타임 의존부트스트랩은 POSIX sh + git만 요구한다. Node는 skills CLI 경로를 쓸 때만 필요하고, 없으면 심링크 경로로 폴백한다.
NFR-4오프라인 동작저장소 클론만 있으면 네트워크 없이 심링크 모드로 설치된다.
NFR-5비파괴덮어쓰기 전 타임스탬프 백업을 남긴다. 백업 없는 덮어쓰기 경로가 존재하지 않는다.
NFR-6플랫폼macOS와 Linux. Windows는 WSL 경유만 고려한다.

비밀 취급 원칙

공개 저장소와 설정 복원을 동시에 하기로 한 결정이 이 제품의 가장 큰 제약을 만든다. 설정 파일은 원래 비밀이 모이는 곳이다. 따라서 경계를 문서가 아니라 구조로 긋는다.

저장소에 들어가는 것 / 들어가지 않는 것

구분내용형태
포함설정의 형태 — 어떤 hook을 어떤 이벤트에 걸지, 어떤 MCP 서버를 어떤 명령으로 띄울지, 어떤 권한을 허용할지*.tmpl 템플릿
포함비밀이 필요한 자리와 그 이름${TAVILY_API_KEY}
제외토큰·API 키·auth.json·.credentials.json의 실제 값환경변수 또는 OS 키체인
제외회사 내부 호스트명, 고객사명, 사내 경로가 박힌 스킬별도 private 저장소로 분리
제외세션 로그, 히스토리, 캐시.gitignore

강제 수단

  • 템플릿 전용 — config/에는 .tmpl만 커밋한다. 실값 파일은 .gitignore가 막는다.
  • CI 비밀 스캔 — 모든 푸시에서 스캔하고, 발견 시 실패시킨다 (FR-7).
  • 부트스트랩의 비침습 규칙 — 병합 시 기존 파일의 비밀 필드는 읽지도 쓰지도 않는다. 자리표시자가 해석되지 않으면 그 항목을 건너뛰고 사용자에게 알린다.
  • 사고 대응 절차 — 실수로 커밋한 경우 히스토리 재작성이 아니라 즉시 키 회전이 1순위임을 README에 명시한다. 공개 저장소에 올라간 값은 이미 유출된 것으로 간주한다.
